# 从已合并的改动里学到的

AGENTS.md 里那些规矩不是凭空来的，每条底下都有一次具体的翻车。这里记它们：
**规则 → 为什么 → 证据**。规则被撞够 3 次才迁进 AGENTS.md 当"规矩"。

## 怎么用

- **改代码前先读一遍。** 正要动的地方被某条规则覆盖时，先看它的来历再动手。
- **记新条目必须带证据**：提交号、日期、现象（有测量就带测量）。"我觉得这样更好"不算。
- **`Seen` 记的是这条规则被违反（或差点被违反）的次数**，不是同意的次数。
  第 3 次被撞上的规则才迁进 AGENTS.md，迁了之后两边都要读——AGENTS.md 是正文，
  这里是来历。没到 3 次的先在这里攒着，别把一时偏好写成一生的标准。
- **「写测试了」「改好了」不算验证。** 要写清跑了什么、坏了哪行代码才变红、什么没验。

## 1. 渲染层的性能手法，必须验证"真实交互路径"

**规则**：给列表 / 滚动容器加 `content-visibility`、虚拟化、占位高度这类优化时，验收不只看
滚轮和帧率，必须真的拖动滚动条、真的点按滚动；CSS 层面的"提速"先写出可验证的预期再上。

**为什么**：滚轮滚动由合成器线程完成，主线程再卡也看着顺；滚动条拖动是主线程滚动，
浏览器不会拖过"还只有猜测高度"的行。只用滚轮验收，会把坏掉的拖动完全遮住。

**证据**：

- `7eb81ff`（2026-09-18）给字幕行加 `content-visibility: auto` 换一次挂载提速（主线程
  380ms → 214ms）。
- `46da8d8`（2026-10-16）整体回退。用真实样式表 + 1187 条字幕复现（headless Chrome 155 /
  Edge 155，CDP 真实拖动）：被跳过的行在纵向 flex 里被压成 padding 高度，列表
  `scrollHeight` 只有 ~32k px（真实 ~176k，差约 5 倍）；滚动条拖动只能到列表 17%；把压扁
  修掉后仍封顶 ~51% 且与拖动速度无关；同时程序化滚动能到 100%、滚轮看着一直正常——
  **拖动坏了一个月没人定位，因为滚轮把它盖住了**。
- 回退代价：一次性挂载 +约 110–170ms（只在打开大任务时付一次）。挂载提速要另找正路
  （真正的窗口化列表），不许再上 `content-visibility`。

**Seen**：1×（`46da8d8`）

## 2. 结构性数字只有一个出处，别让"列清单"手抄第二遍

**规则**：SQLite 列与 VALUES 占位符、字段的 store/hydrate/转换表、批大小、契约常量——
这些"改一处要记得同步 N 处"的结构性清单，必须收敛到单一出处（引用同一常量 / 同一函数），
并配一条守护测试；改动前 grep 其余手抄处。

**为什么**：手抄清单的漂移不会有编译错误，只会在运行时整片坏掉（保存全失败、批次行为与
文档不符），而且每次都只报最先撞上的那一个位置。

**证据**：

- `62ac344`（2026-09-10）：settings upsert 列清单 27 列、VALUES 写了 28 个值，**保存设置
  全部失败**（GUI 保存键、CLI 写入、模型目录、术语编辑全灭）；由既有的
  `save_then_load_roundtrips_settings` 测试兜住。
- `62501b4`（2026-09-11）：批大小两处定义（README 写 8、桌面链路实际传 20），拆分梯度
  从 20 直接掉到 4，行为与文档不符。
- 更早的同构：`4bddccf` / `952e8e8`（2026-06-08/09）新增 intent/max_retries 列要同时改
  conversion + store + hydrate 多处手写表。

**Seen**：3×（2026-06-08/09 同构一次；2026-09-10；2026-09-11）→ 已迁入 AGENTS.md
